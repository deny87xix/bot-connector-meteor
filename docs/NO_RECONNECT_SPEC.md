# ТЗ: `.bot enter/back` без перезахода, Meteor/Baritone за бота без входа, GUI

Статус: спецификация, код не написан. Реализовывать там, где есть рабочий Gradle и jar Minecraft 1.21.11
(API сверять через `javap`, не по памяти).

## 1. Цель

1. `.bot enter <ник>` и `.bot back` переключают управление **без перезахода клиента** и без обмена ников/сессий.
2. `.bot <ник> baritone <команда>` и `.bot <ник> meteor ...` работают за бота, **не входя в него**.
3. GUI: сохранённые боты, запуск/остановка, логи, вход в бота, Meteor и Baritone от имени бота, ввод команд Baritone.
4. Подсказки (tab-complete) в `.bot <ник> baritone <команда>`, как у обычного Baritone в чате (`#go` -> `goto`).

## 2. Как сейчас и почему это мешает

- Бот = headless: прокси-слушатели пакетов (`BotConnector`), свои чанки (`BotWorld`), своя физика (`BotSim`).
- Meteor и Baritone читают глобальное состояние клиента: `mc.player`, `mc.world`, `mc.interactionManager`,
  сетевой обработчик игрока. У headless-бота этого состояния нет, поэтому `BotSwap` перезаходит клиентом под его ником.
- Следствие: нужен offline-mode, «тело-бот» для вашего ника, задержки в тиках (`after(70)`, `after(100)`),
  гонки `busy`.
- GUI у аддона нет: всё через команды `.bot ...`; `BotSwap.openGui()` лишь открывает стандартное окно Meteor.

## 3. Целевая архитектура

### 3.1. «Настоящий» бот
Бот держит полное клиентское состояние, как обычный клиент:
`ClientConnection`, `ClientPlayNetworkHandler`, `ClientWorld`, `ClientPlayerEntity`, `ClientPlayerInteractionManager`.
Соединение проходит login -> config -> play стандартным путём (как `ConnectScreen`), но **не становится главным**.

### 3.2. Примитив «окно контекста»
Ванильные обработчики и Baritone/Meteor используют глобальные поля `MinecraftClient`. Поэтому всё, что относится к
боту, выполняется внутри окна:

```
BotContext.run(bot, () -> { ... })
  1. сохранить mc.{world, player, interactionManager, cameraEntity, ...} (контекст пользователя)
  2. подставить состояние бота
  3. выполнить действие (conn.tick(), Baritone tick, тик модулей)
  4. забрать изменения (например, мир/игрок, созданные onGameJoin) обратно в Bot
  5. вернуть контекст пользователя (finally)
```

Окно открывается только на главном потоке, не вкладывается (проверка на повторный вход).

Важно: `ClientPlayNetworkHandler.onGameJoin` сам кладёт мир и игрока в `mc` (через `joinWorld`). Для бота это надо
перехватить (mixin с флагом `BotContext.active` или чтение полей `mc` после окна и откат), чтобы фоновый бот не
подменял мир пользователя и не трогал рендерер/экраны.

### 3.3. `enter` / `back` без перезахода
- `enter`: окно становится «постоянным»: `mc.world/player/interactionManager/cameraEntity` = бота;
  `worldRenderer.setWorld`, `particleManager`, камера, HUD; клавиатурный ввод назначить игроку бота
  (`player.input`).
- Пока вы в боте, **ваше** соединение продолжает жить: его надо тикать (keep-alive, пакеты движения) в собственном
  окне, иначе сервер вас кикнет по таймауту. Тело-бот больше не нужен.
- `back`: обратный порядок; ввод бота заменить на нейтральный (бот стоит), вернуть ваши поля и рендерер.
- Убрать из `BotSwap`: смену `Session`, `CrackedAccount.login`, `keepBody`, отложенные задачи по тикам.
  Ограничение «только offline-mode» остаётся только для headless-логина бота (шифрование не реализовано).

### 3.4. Baritone за бота без входа
- Взять экземпляр Baritone бота: `BaritoneAPI.getProvider()` (проверить в jar: `getBaritoneForPlayer`,
  `getBaritoneForConnection`, `createBaritone`). Нужен **отдельный экземпляр на бота**.
- Тик этого экземпляра выполнять в окне контекста бота каждый клиентский тик. Команды `.bot <ник> baritone ...`
  отправлять в его `ICommandManager`.
- Проверить: `PlayerContext` Baritone берёт `mc.player` напрямую, значит без окна работать не будет.

### 3.5. Meteor за бота без входа (исследовательский этап)
Модули Meteor — глобальные синглтоны, состояние `active` общее. Варианты:
- **A.** Свой лёгкий набор «модулей бота» в аддоне (Killaura-lite, AutoEat и т. п.), без Meteor GUI. Надёжно, но это
  не «чистый Meteor».
- **B.** В окне бота временно применять набор модулей из `BotModules`, постить `TickEvent.Pre/Post` в Orbit
  `EVENT_BUS` и возвращать набор пользователя. Риски: побочные эффекты `onActivate/onDeactivate` каждый тик,
  рендер- и GUI-модули не работают, ваши модули на это время приостановлены.
- Решение выбрать после этапов 0-3 по результату замеров. Начать с B для одного бота, и только тиковых модулей.

### 3.6. Профили и логи (основа для GUI)
- **Сохранение.** `BotProfileStore` (`config/bots-addon/bots.json`) хранит на бота: ник, адрес, флаг «автозапуск»,
  историю команд Baritone. Набор модулей Meteor бота остаётся в `modules.json` (`BotModules`).
- **Три разные операции** (сейчас `remove` смешивает их):
  - **Запустить** (`connect` из сохранённого профиля);
  - **Остановить** (`BotManager.suspend`: отключить, профиль оставить);
  - **Удалить** (`BotManager.remove`: отключить и забыть профиль).
- **Логи.** У каждого `Bot` кольцевой буфер (например, 500 строк) с временем и уровнем. Источники:
  состояния (`Bot.set`), чат сервера и `echo()` из `BotConnector`, причина дисконнекта и «последние пакеты»,
  вывод Baritone этого бота (перехват `settings.logger` его экземпляра). Буфер потокобезопасный, GUI читает копию.
  Команда `.bot log <ник> [N]` печатает последние N строк в чат.

### 3.7. GUI (вкладка «Bots» в Meteor)
Реализовать на GUI-библиотеке Meteor (`GuiTheme`, `Tab`/`TabScreen` или `WindowTabScreen`, `WTable`, `WButton`,
`WTextBox`, `WLabel`; точные классы сверить по jar Meteor `1.21.11-SNAPSHOT`). Регистрация: `Tabs.add(...)` из
точки входа аддона; плюс команда `.bot gui`.

Экран делится на две части.

**Слева: список ботов** (таблица)
ник, сервер, состояние (`Bot.State`), координаты; кнопки: Запустить / Остановить / Удалить, Войти (`enter`),
Вернуться (`back`, видна, когда вы внутри бота). Внизу форма «Добавить бота»: поля ник и адрес, кнопка Connect;
ник валидируется `BotManager.validNick`. Список обновляется по тику.

**Справа: панель выбранного бота** (три вкладки)
1. **Логи**: прокручиваемый вывод буфера из 3.6, автоскролл, кнопки Очистить и Копировать.
2. **Baritone**: поле ввода команды + кнопка Отправить, под полем список подсказок (см. 3.8), история команд
   (стрелки вверх/вниз), быстрые кнопки `stop`, `goto`, `follow`, `mine`, `cancel`.
3. **Meteor**: переключатели модулей для этого бота (`BotModules`), кнопка «Открыть Meteor от имени бота»
   (`.bot <ник> meteor`).

Привязка к ядру: пока этапы 2-4 не сделаны, кнопки Войти / Baritone / Meteor вызывают текущий `BotSwap` (с
перезаходом); после этапов 2-4 те же кнопки работают без перезахода. GUI не знает, как это устроено внутри, общается
только через фасад `BotService` (connect/stop/delete/enter/back/runBaritone/setModule/logs).

### 3.8. Подсказки в `.bot <ник> baritone <команда>`
Как обычный чат Baritone: по `Tab` или в списке подсказок `#go` дополняется до `goto`, после команды подсказываются
аргументы (`goto` -> координаты/блоки, `mine` -> имена блоков и т. п.).

- На аргументе `command` (`greedyString`) добавить `.suggests(...)`: взять строку после ника, убрать префикс
  Baritone (`BotBaritone.prefix()`, обычно `#`, если пользователь его ввёл), передать в менеджер команд Baritone
  (`ICommandManager.tabComplete(String)`: проверить точную сигнатуру в jar Baritone) и вернуть варианты через
  `SuggestionsBuilder`.
- Для `greedyString` Brigadier считает всё одним токеном, поэтому смещение подсказки нужно вычислять самому:
  строить `builder.createOffset(...)` на позицию последнего слова.
- Подсказки команд не зависят от бота (набор команд Baritone общий), поэтому **работают уже сейчас**, до этапов 2-4.
  Для подсказок аргументов, зависящих от мира (`goto` по блокам), нужно окно контекста бота (после этапа 3);
  до того использовать мир пользователя и пометить это в коде.
- Те же подсказки переиспользуются в поле ввода Baritone в GUI (3.7).
- Когда вы внутри бота, в обычном чате подсказки `#...` даёт сам Baritone, дублировать их не нужно.

## 4. Этапы и критерии приёмки

**Этап 0. Разведка по jar (1.21.11, Yarn).** Через `javap` выписать: конструкторы `ClientPlayNetworkHandler`,
`ClientConnectionState`, `ClientWorld`, `ClientPlayerEntity`, `ClientPlayerInteractionManager`; поля `MinecraftClient`
(`world`, `player`, `interactionManager`, `cameraEntity`), `joinWorld`, `getNetworkHandler`; путь `ConnectScreen` ->
`ClientLoginNetworkHandler` -> `ClientConfigurationNetworkHandler`; классы GUI Meteor и API Baritone
(`ICommandManager.tabComplete`, `getBaritoneForPlayer`). Результат: `docs/api-notes.md`.

**Этап G1. GUI без зависимости от нового ядра (можно параллельно с 0-1).** Фасад `BotService`; профили и операции
Запустить / Остановить / Удалить; буфер логов и `.bot log`; вкладка «Bots» со списком, формой добавления и панелью
логов; подсказки Baritone в команде. Приёмка: бот сохраняется между перезапусками клиента; Остановить не стирает
профиль, Удалить стирает; логи видны в GUI и в `.bot log`; `.bot <ник> baritone go` + Tab даёт `goto`; все действия
из GUI работают без ошибок в `latest.log`.

**Этап 1. Настоящий бот в фоне.** Бот заходит на сервер ванильным путём, держит свой мир, не влияет на ваш мир/экран.
Приёмка: 2 бота + ваш клиент на локальном сервере (`online-mode=false`), чанки видны только в своих мирах, никаких
ClassCastException от Meteor (события пакетов бота не доходят до модулей Meteor вне окна).

**Этап 2. `enter` / `back`.** Приёмка: переключение туда и обратно 20 раз подряд без перезахода, без кика по таймауту,
ваш прежний персонаж на сервере не пропадает и не телепортируется, рендер мира корректен, управление идёт в нужного
игрока. Кнопки Войти / Вернуться в GUI работают на новом ядре.

**Этап 3. Baritone за бота.** Приёмка: `.bot <ник> baritone goto x y z` ведёт бота, пока вы стоите/играете за себя;
два бота с разными целями одновременно; вкладка Baritone в GUI отправляет команды и показывает вывод в логах бота;
подсказки аргументов учитывают мир бота.

**Этап 4. Meteor за бота.** Приёмка: Killaura (и ещё 2 тиковых модуля) работает за бота без входа; ваш набор модулей
не меняется; `.bot back`/тики не сбрасывают состояние; переключатели во вкладке Meteor работают.

**Этап 5. Чистка.** Удалить или оставить `BotSim`/`BotWorld`/прокси-слушатели как «лёгкий режим» (много дешёвых
ботов); обновить README; убрать `AddonTemplate`/`com.example` из имён.

## 5. Риски

- Память и CPU: у каждого настоящего бота свой `ClientWorld` и чанки. Ограничить дальность прорисовки бота.
- Подмена мира в рендерере (`worldRenderer`, звук, частицы) — самая хрупкая часть, делать за флагом, с откатом.
- Многопоточность: пакеты приходят из сетевого потока, всё состояние трогать только на главном; логи и профили
  читать из GUI только через копии.
- GUI Meteor: API экранов и виджетов меняется между снапшотами, брать классы из jar, не по памяти.
- Версия: каждая правка API проверяется чистой сборкой (`gradlew clean build`), не инкрементальной.

## 6. Что оставить как есть
Хранилище профилей (`BotProfileStore`, расширить полями), валидацию ников, команды `connect/remove/clear/list/chat`.
Дисклеймер из README (боты только на своих серверах или там, где это разрешено правилами) сохранить.
